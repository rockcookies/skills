# 层级模型

## 三层文档

用三层，加载与阅读预期不同：

1. **Agent 指令（`AGENTS.md`）** — 简洁、可执行的规则，影响 Agent 在某目录作用域怎么干活。
2. **人入口（`README.md`）** — 向尚未摸过代码的人解释项目、服务、包、示例或工具。
3. **深文档（`docs/`）** — 架构、设计决策、runbook、API 参考、排障、领域说明。需要时从相关入口或指令文件链过去。

不要把这三层压成一份过大的文件。

## 指令继承与作用域

把一份 `AGENTS.md` 视为作用于其目录及后代，除非目标 Agent 另有优先级语义。在子树工作时，有效指令是从根到最近后代的适用祖先文件。子文件应补充或收紧本地约束；不要默默与父文件矛盾。

示例：

```text
repo/
├── AGENTS.md                 # 全局工作流与全仓不变量
├── README.md                 # 产品/项目入口
├── docs/
│   ├── architecture.md       # 稳定架构，不是每次都加载的规则
│   └── operations.md
├── backend/
│   ├── AGENTS.md             # 后端专用命令与边界
│   ├── README.md             # 仅当 backend 是可独立使用的组件
│   └── internal/
│       └── billing/
│           └── AGENTS.md     # 仅当 billing 有独有本地规则
└── frontend/
    └── AGENTS.md             # 前端专用工作流与不变量
```

这是示意，不是必选目录布局。

## 何时加嵌套 AGENTS.md

仅当下列全部成立时才加：

- 子树是有意义的工作边界（包、服务、应用、领域、生成代码区或独立工具链）。
- 有祖先指令覆盖不好的本地规则。
- 这些规则很可能在多次未来任务里仍有用。
- 预期收益超过额外上下文与维护成本。

好的理由包括：独立测试命令、代码生成约束、禁止的依赖方向、安全边界、迁移规则、领域不变量。

弱理由包括：只是文件多、只是某语言目录且无特殊规则、重复根风格规则、描述显而易见的文件夹内容。

## 根 AGENTS.md 预算

目标是 Agent 能快速扫完的紧凑文件。大约 60–120 行是有用的复核阈值，不是硬规格。变长了就把细节路由到嵌套指令或 `docs/`。只留高价值的全局约束和命令。

嵌套指令通常应比根文件短。嵌套文件过长，说明该把稳定说明与可执行规则拆开。

## README.md 放哪里

根 `README.md` 通常是公开入口。嵌套 README 在子树可独立理解或使用时有用，例如：

- 有自己公开 API 的可复用库/包；
- 有独立安装/配置的可部署服务；
- 有独立执行步骤的示例/demo；
- 面向不同读者的工具或应用。

不要只为描述每个文件夹建嵌套 README。对内部包，若源码注释、包文档或相关 `docs/` 页更好找，优先那些。

## 客户端专用指令文件

只维护 `AGENTS.md` 作为 Agent 指令入口；Claude Code 直接读它。不要新建 `CLAUDE.md`。仓库里已有的 `CLAUDE.md`、`GEMINI.md` 或其他客户端专用文件，不当作第二份正文维护，也不主动与 `AGENTS.md` 同步；除非用户明确要求，否则不删。
