# 内容落点：AGENTS.md vs README.md vs docs/

创建或编辑文档前读这份指南。同一次改动可能影响多类读者，但内容要按读者重写，不要原文照抄到多处。

## 落点矩阵

| 信息 | 主落点 | 次落点 |
|---|---|---|
| 构建、测试、lint、生成命令与工作目录 | 根或归属 `AGENTS.md` | 用户需要时写进根 README 快速开始 |
| Agent 工作流、评审期望、禁止动作 | `AGENTS.md` | 无（只维护 `AGENTS.md`；见 hierarchy-model） |
| 包边界与依赖方向规则 | 归属嵌套 `AGENTS.md` | 架构文档写理由 |
| 仓库用途与功能摘要 | 根 `README.md` | 无，除非独立组件需要自己的 README |
| 安装与第一次跑通 | 根或组件 `README.md` | 进阶部署用运维指南 |
| 公开配置变量与示例 | README 或配置参考 | `AGENTS.md` 只写 Agent 编辑约束 |
| 公开 API、CLI 语法、集成示例 | README 或 `docs/api/` | `AGENTS.md` 写兼容/测试约束 |
| 内部架构、时序图、组件关系 | `docs/architecture/` | 从 README/AGENTS.md 短链过去 |
| 已采纳/否决的技术取舍与理由 | `docs/adr/` 或现有 ADR 位置 | `AGENTS.md` 只写由此导出的可执行约束 |
| 生产事故流程与恢复步骤 | `docs/operations/` 或 runbook | 改运维相关代码时，`AGENTS.md` 写安全约束 |
| 给人看的贡献流程 | README 或 CONTRIBUTING.md | `AGENTS.md` 写 Agent 专用检查与行为 |
| 生成文件与重新生成命令 | 归属 `AGENTS.md` | 仅当用户会消费生成物时写进 README |

## README.md 是第一类文档

盘点或审计时不要忽略 README。决定新建文档前，先检查根和嵌套 README。

README 应回答适合其读者的问题：

- 这是什么项目/组件，给谁用？
- 需要什么前置条件？
- 用户怎么安装、配置、运行或接入？
- 支持的入口和重要限制是什么？
- 更深的文档维护在哪里？

根 README 要在不强迫读者理解仓库内部目录布局的前提下有用。链到更深材料，不要塞进全部架构细节。

嵌套 README 不能替代包级 API 文档或 Agent 指令。只有子树有独立的人类读者时才建。

## 改动 → 文档决策

### 通常改 README.md 当

- 安装、搭建、构建或首次运行步骤变了；
- 用户可见功能、端点、CLI、公开 API 或示例变了；
- 支持的运行时、依赖、部署拓扑或兼容性变了；
- 配置项增删改名或含义变了；
- 已文档化的限制、安全要求或运维前置变了。

### 通常改 AGENTS.md 当

- 正确的本地构建/测试/lint/生成工作流变了；
- 目录归属或包边界变了；
- 编码不变量、依赖规则、迁移约束或生成代码政策变了；
- 发现可重复的 Agent 失败模式，并能压成简短动作；
- 现有指令不再为真。

### 通常改 docs/ 当

- 架构或数据流说明变了；
- 决策需要理由、备选与后果；
- 详细流程、API 参考或运维 runbook 变了；
- 图示或跨组件说明会把 AGENTS.md 或 README.md 撑得过大。

### 通常不改文档当

- 私有实现重构，已文档化的契约或工作流未变；
- 符号改名，但公开示例、路径或指令都没引用它；
- 加了测试，但测试命令、覆盖期望或已文档行为未变；
- 措辞可以更漂亮，但仍然正确清楚。

## 避免双头文档

同一事实需要出现在两份文档时，指定一处权威详述，另一处链接过去。例如：

- README：「后端测试命令见 `backend/AGENTS.md`。」
- AGENTS：「公开安装说明维护在 `README.md`。」
- README：「架构概述：`docs/architecture/overview.md`。」

不要把大段命令或政策复制到多处。若一小条命令必须出现在两类读者的文档里，两边都要核实并保持一致。
