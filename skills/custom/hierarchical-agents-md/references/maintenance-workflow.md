# 维护工作流

## 感知改动的更新算法

1. **划定范围。** 记下分支/base ref，或任务关心的是暂存、未暂存还是已提交改动。
2. **收集改动路径。** 用 `scripts/changed_files.py`；仔细看重命名和删除。
3. **读相关 diff。** 按领域/包分组，把源码、测试、配置、CI 和公开契约一起看。
4. **解析文档归属。** 对每个改动路径，找最近适用的 `AGENTS.md`；祖先/根 README 候选另算。
5. **判断已文档化的事实是否变了。** 文件改了是影响信号，不是必须改文档的证明。
6. **读当前文档。** 搜被改动影响的旧名、路径、命令、配置键、示例和陈述。
7. **起草最小修改。** 替换过时材料，合并重复，删掉作废规则，只加已证实的要求。
8. **校验。** 跑 `scripts/audit.py`，看 diff，在可行时跑相关仓库检查。
9. **报告。** 说明每份文档为何改，或为何有意不改某候选。

## 审计严重级别

在 Agent 写出的审计报告里用这套级别：

- **P0 — 错误 / 不安全：** 文档正引导用户或 Agent 去做损坏、不安全或不兼容的动作。先修。
- **P1 — 实质过时：** 安装、命令、API、配置、架构边界或关键工作流已与仓库不符。
- **P2 — 结构债：** 重复/冲突规则、落点错误、过长，或缺失妨碍导航的链接。
- **P3 — 文案：** 清晰度、格式、命名一致或可选示例。不要压过正确性。

静态脚本能发现断链和可疑结构。语义严重级别需要读相关源码证据。

## 安全编辑政策

- 不要用模板覆盖一份已有实质内容的 README 或 AGENTS.md。
- 不要只因模板里没有就删内容。先判断它是否承载项目特有的不变量或决策。
- 大重组时，除非用户明确要求直接执行，否则先出逐文件提案。
- 拆文档时，同一次改动里保留入站链接并更新引用。
- 合并文档时，保留独有事实，并显式化解矛盾。
- 生成或 vendored 文档仍按其既有生成/归属政策处理。
- 纯文档任务不要改应用源码，除非用户明确要求，且为了让已文档化的命令/路径成立所必需；改了要说明。

## 建议的更新报告

```markdown
## Documentation update

| File | Action | Reason / evidence |
|---|---|---|
| `backend/AGENTS.md` | Updated | Test command changed in `backend/Makefile` |
| `README.md` | Unchanged | Public setup and usage are unaffected |

### Validation
- `python scripts/audit.py .` — passed
- `go test ./...` (from `backend/`) — passed

### Follow-ups
- None
```

只写实际执行过的检查。没跑过的检查要说没跑。
