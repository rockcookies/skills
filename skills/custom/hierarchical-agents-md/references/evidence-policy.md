# 证据政策

文档维护是源码核实任务。Agent 必须把仓库里观察到的事实，与假设、提案分开。

## 证据优先级

按下列顺序取证，并按所核说法调整：

1. 可执行源码与配置：代码、构建脚本、manifest、应用配置、部署清单。
2. 测试与夹具：断言、集成搭建、测试脚本、契约测试。
3. CI 与发布自动化：实际命令与支持的环境。
4. 已有文档：有用上下文，但不能单独证明说法仍真。
5. 注释、提交说明、issue 笔记、设计讨论：辅助上下文，可能过时。

核命令时，看被调用的任务/脚本及其工作目录。核公开 API 时，看导出符号、路由、schema 或生成契约。核架构时，看装配/组合根和相关调用路径，不要只靠目录名。

## 分析时的说法标签

用这些内部标签（不必全部出现在最终文档里）：

- **已确认** — 当前源码/配置/测试/CI 直接支撑。
- **相互印证** — 多个独立仓库信号支撑。
- **推断** — 从结构或命名看合理，但未直接核实。
- **未知** — 现有证据建立不了。

把已确认或相互印证的事实写成项目规则。不要把推断或未知写成陈述性文档。要么继续查，要么省略。

## 可追溯性

对不明显的陈述，在有助于后人核实处附上简短源路径。不要给琐碎事实塞满引用。

例子：

- 「在 `backend/` 跑 `go test ./...`（模块根：`backend/go.mod`）。」
- 「不要改 `api/generated/`；用 `make api-generate` 重新生成（`Makefile`）。」

永远不要编造路径、命令、环境变量、依赖、服务、负责人或支持承诺。

## 新鲜度与 Git 指纹

用 Git diff 找可能漂移。默认不要往文档里写死提交哈希或时间戳：它们自己会过期，即便文档化行为仍然正确。

只有项目确实需要跟踪一小撮关键源依赖时，才值得上指纹/清单系统。若引入，保持机器维护，精确定义什么变化会使文档失效，并且不要把指纹元数据抄进人读的 README。

## 秘密与敏感数据

不要把密钥、令牌、私有主机名、个人数据、生产凭证或本地 `.env` 的值写进文档。优先用变量名和安全占位符。示例值写入前先确认是否本来就公开。

## 无依据的说法

没有仓库证据，不要声称「已测试」「受支持」「生产就绪」「安全」「高性能」「向后兼容」一类性质。把意图行为与测试或代码强制的行为分开写。
