# Skill Evolution

把一份依赖提示词的 Skill 说明，逐步改造成可维护的工作系统。只改进能解决已观察到的问题的部分；保留有效行为，改动规模与任务成正比。

## 编排

**完成标准：** `writing-for-agents` 的 SKILL.md 已读入；若目标含 `SKILL.md` 改写，其 `SKILL-MECHANICS.md` 也已读入；或已点名缺失并停止。

1. 读取 `writing-for-agents` 的 SKILL.md 并按其执行。缺则报告并停止，不要假装模拟。
2. 本轮将改写或新写目标 `SKILL.md` 时，再读 `writing-for-agents` 的 `SKILL-MECHANICS.md`（frontmatter、调用方式、router）。缺则同样停止。
3. 其后阶段的文案判断（指针、层级、完成判据、leading words、剪枝）一律按已加载的 `writing-for-agents`，不把该 skill 正文抄进本文件。

## 操作约定

1. **先检查，后编辑。** 阅读目标 `SKILL.md`、被引用的 references、脚本、fixtures、样例，以及相关的项目说明。不要仅凭用户的口头概述就开始大规模重写。
2. **先诊断，后提方案。** 先给出简明诊断。诊断阶段不得编辑目标文件。
3. **确认验收契约。** 提出拟定的 must-have、偏好、不可接受的失败，以及需要人工批准的边界。只问缺失的决策，每轮最多三个问题。优先复用 Skill、样例和对话中已有的证据。
4. **重大修改前先等待确认。** 用户批准范围与标准之前，不得修改目标 Skill。若用户已明确授权实施并给出标准，视为已批准。只读检查和验证无需批准。
5. **增量改动。** 保留现有的好行为。优先小而可回滚的改动。除非观察到的工作流确有需要，否则不要新增 CLI、框架、数据库或目录层级。
6. **验证要有证据。** 没有实际运行并留有证据的检查，不得宣称通过。严格区分自动检查、AI 评估、人工确认和未验证项。
7. **保护用户成果。** 编辑前先检查仓库状态。未经明确批准，不得覆盖原始样例、正式交付物或重要文件。除非用户要求，不要 commit、push、发布或修改权限。
8. **安全停止。** 检查失败时，应诊断并修复原因，而不是削弱或删除检查。同一操作连续三次失败后，停止并报告阻塞点，给出最小的下一步行动。

## 输入与范围

根据用户给出的路径确定目标 Skill 目录。若路径缺失且无法从当前工作区推断，只问一个直接的问题来获取路径。

默认范围：

- 目标 Skill 目录及其明确引用的文件；
- 直接相关的测试、样例和项目级说明；
- 为完成已批准改动所需的最小支撑文件。

不要扫描无关仓库或用户数据。只在必要且安全时才跟随 symlink 和外部引用；无法访问被引用资源时要如实说明。

## 工作流

### Phase 1 — 了解现有 Skill

**完成标准：** 已确认目标路径含 `SKILL.md`；已读完入口与本地引用；已记录 baseline（文件清单、重要行为、已有检查、已知失败）；缺失引用已标为 gap，未编造内容。

1. 确定目标路径，并确认其中存在 `SKILL.md`。
2. 完整阅读 `SKILL.md`，跟进本地引用，检查相关脚本、模板、fixtures 和样例。
3. 检查适用于目标路径的仓库说明（`AGENTS.md`、`CLAUDE.md`、贡献指南、测试说明）。
4. 在可用时检查 `git status` 和相关的近期历史。不要 reset、stash、clean 或丢弃用户的改动。
5. 记录 baseline。

### Phase 2 — 诊断并梳理工作地图

**完成标准：** 诊断覆盖下表五轴；发现已按 Blocker / High / Medium / Low 分级；未把「文档更长」当作改进；工作地图有助于理解时已引用或填写 `references/work-map.template.md`。

| 维度 | 检查对象 | 要回答的问题 |
|---|---|---|
| 工作地图 | 目标、触发条件、步骤、输入/输出、依赖、分支、失败路径 | Agent 能否知道下一步做什么、什么算完成？ |
| 工具能力 | 现有脚本、CLI、API、MCP 工具、命令、可复用操作 | 哪些步骤是确定性的且已有支持？哪些重复步骤脆弱或靠手工？ |
| 验证机制 | 命令、断言、fixtures、样例输出、审核关卡 | 什么证据能证明正确？哪些要求只有文字、没有检查？ |
| 反馈机制 | 用户纠正、issue 记录、样例、回归测试、变更历史 | 一次纠正能否避免同类问题再次发生，又不会形成过度泛化的规则？ |
| 文案杠杆 | 按已加载的 `writing-for-agents`：context pointer、信息层级、完成判据、leading words、剪枝 | description/触发是否过宽或过窄？步骤与 reference 是否错位？完成界是否可检查？有无重复/沉淀/否定式禁令？ |

分级：

- **Blocker：** 阻碍正确或安全的执行。
- **High：** 反复导致错误或无法验证的输出。
- **Medium：** 造成可避免的手工工作或不一致。
- **Low：** 可读性或可选的打磨。

### Phase 3 — 确认验收标准

**完成标准：** 已向用户提出拟定契约（Must / Should / 不可接受的失败 / 人工关卡 / 自动化边界 / 保留项）；本轮最多三个决策问题；用户已批准主范围，或未答非关键偏好时已采用最安全默认并说明。

实施前先总结拟定的契约。需要长期记录时，使用 `references/acceptance-criteria.template.md`。

涵盖：

- **Must：** 必须通过的、可客观测试的要求。
- **Should：** 有价值但可以取舍的偏好。
- **不可接受的失败：** 回归、不安全的副作用、无依据的结论或反复出现的错误。
- **人工关卡：** 需要用户判断或明确授权的决策。
- **自动化边界：** Agent 在已批准范围内可自主执行的动作。
- **保留项：** 必须保持不变的文件、接口、样例和行为。

### Phase 4 — 设计最小而有用的改进

**完成标准：** 每项拟议改动都有 Phase 2 诊断与 Phase 3 契约支撑；无投机性重构；工具/检查/反馈路径已按下列子节选定。

#### 4.1 结构化工作流

明确目的、激活条件、前置条件、步骤、决策分支、输出和完成定义。优先紧凑的工作地图和明确的停止条件。

#### 4.2 把重复的确定性工作工具化

对每个候选操作，判断应当：

1. 复用现有工具或命令；
2. 为确定性、可重复的工作新增一个小脚本；
3. 保留为 Agent 推理（依赖上下文或主观判断）。

CLI 是可选项，不是默认项。新增工具时，定义输入、输出、退出行为、错误、幂等性和安全使用边界。除非有充分理由，优先标准库。对破坏性或大范围改动，尽可能提供 dry-run。

#### 4.3 让要求可验证

在可行时，把客观要求转化为检查。每个检查应说明：检查什么；怎么检查；预期结果；实际结果；证据。

内容变化后，重新执行受影响的检查。不要用自动化假装主观质量是客观的：语义正确性、视觉质量、语气和领域判断，应保留为 AI 评估或人工审核。

#### 4.4 建立有边界的反馈闭环

对每条有意义的纠正，使用 `references/feedback-entry.template.md`（或已有的 issue 系统）记录反馈。然后：

1. 明确指出被违反的具体预期及证据；
2. 分类为：单次要求、环境特定约束、反复出现的缺陷或新的产品需求；
3. 调查根因；
4. 选择最窄的持久修复；
5. 在可行时添加回归样例或检查；
6. 优先更新工具行为或认可样例，再考虑增加文字说明；
7. 只有当 Agent 的决策或工作流确实需要改变时，才更新 Skill 指令；
8. 验证修复既能防止已报告的失败，也没有破坏已有用例。

没有证据或用户批准，不要把一次性偏好升级为全局规则。合并重叠规则，删除过时或相互矛盾的规则。

### Phase 5 — 小批量实施

**完成标准：** 已批准范围内的最小自洽改动已落地；样例/测试/校验器与所保护行为同步更新；未静默改 baseline 样例；超出批准范围的兼容性变更已停下询问。

1. 重新确认已批准的范围和当前工作区状态。
2. 做最小的、自洽的改动集。
3. 保持改动局部化；不要仅为美观而重命名或移动文件。
4. 在所保护的行为旁边，同步添加或更新样例、测试、校验器或脚本。
5. 应用任何有意的兼容性变更前先说明；若超出批准范围，停下来询问。
6. 保留原始 fixtures 和交付输出。新增 fixture，而不是悄悄修改 baseline 样例。

### Phase 6 — 测试与对比

**完成标准：** 已按下列顺序跑完最相关检查；对比了改造前后相对 baseline 的行为；跳过项已写明原因；未为变绿而削弱已有测试。

1. Skill 包的结构校验；
2. 对改动脚本做语法/静态检查；
3. 已有的自动化测试和样例；
4. 针对已报告失败的回归用例；
5. 在可行且已授权时，做真实任务的冒烟测试；
6. AI 评估：语义一致性与歧义；
7. 人工审核：主观判断或需批准的决策。

如果本包的 `scripts/validate_skill.py` 可用，把它当作轻量的结构检查。它不能证明 Skill 的工作流是正确的。

### Phase 7 — 交付并明确验证状态

**完成标准：** 交付总结回答下列六个问题；每项结果只用四种状态之一；无把 AI 审查写成自动化测试；无把用户未批准的项标为人工确认通过。

适用时，必须且只能使用以下四种状态（需要正式记录时，使用 `references/verification-report.template.md`）：

- **自动验证通过** — 具体命令或测试已运行并通过；附证据。
- **AI 评估通过** — 已进行 AI 审查；概述审查依据。这不是自动化测试。
- **人工确认通过** — 有人明确审阅或批准了该项。
- **尚未验证** — 没有足够证据，或检查被跳过/受阻。

交付总结应回答：

1. 改了什么，为什么？
2. 哪些问题现在可以自动检查？
3. 哪些问题仍需 AI 或人工判断？
4. 运行了哪些回归检查，结果如何？
5. 还有什么未验证或受阻？
6. 以后的反馈应如何进入下一轮改进？

## 持续改进协议

当用户之后报告失败或提出改进建议时：

1. 除非消息明确陈述了通用规则，否则把它当作针对某次具体执行的反馈。
2. 定位相关的 Skill 指令、工具、测试或样例。
3. 检查反馈历史中是否已存在同一问题。
4. 可行时复现失败；否则记录证据方面的限制。
5. 提出窄范围的方案：更新样例、测试/检查、修复工具，或修改指令。
6. 若改动会扩大范围、改变外部行为、影响重要文件，或把偏好升级为全局规则，须先获得批准。
7. 实施并运行相关回归检查。
8. 记录处理结果和证据；关闭或取代该反馈条目。

改进闭环：

`Feedback → Reproduce → Classify → Root cause → Smallest durable fix → Regression check → Record evidence`

Skill 并不会因为「改写了自己的提示词」就算自迭代。真正的持久改进，是每一条被接受的反复纠正都落到某个测试、工具、标准样例或决策规则上，使同类缺陷更难发生、更容易被发现。

## 质量与安全规则

- 除非有证据表明有害或过时，否则保留有效的现有行为。
- 优先改样例、测试和工具，而不是让提示词变长。
- 保持 `SKILL.md` 聚焦；把详细模板和流程移到被引用的文件中。
- 避免对特定 Agent 厂商、shell、语言或仓库布局做硬编码假设。
- 未经检查和授权，不要运行不可信脚本或安装依赖。
- 不要在反馈日志、命令输出、fixtures 或报告中暴露密钥。
- 没有证据，绝不宣称成功。
