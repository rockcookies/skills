# 汇报

先旁白，再审查意见。全程中文。本技能写完回复即结束。

## 旁白

3–6 句，固定顺序，一句一事：

1. 确认 `skills/<repoKey>` 是否存在。
2. 规模：N 个技能、M 个文件；若集合是新建的或明显偏小，点明。
3. 方法：提取引用并对磁盘解析；点明精读了全部 SKILL.md，其余按边与孤立节点深读。
4. 条件项一眼：evals / 规则编号 / 仓库级（meta、SYNC、README）做了哪些。
5. 「审查完成」后立刻进入意见正文。

规模足够小时可写「全量读取」——指精读 SKILL.md 加边两端，不是改完整性标准。

## 审查意见骨架

标题：`审查意见：<repoKey> 跨技能引用连通性`

**范围**：N 个技能（点名），M 个文件，覆盖的扩展名。

**方法**：按 extract.md 抽边并对磁盘交叉校验；声明精读了什么、抽查了什么（尤其 GT 是逐条还是抽查）。点明还核了 meta.ts、SYNC.json、README、集合外标识符。

### 总体结论

五个维度各给一句结论（缺产物写跳过原因，不留空维）：

- 悬空引用（路径 / 文件不存在）
- 集合内技能互引（边数；零边是观察而非自动缺陷）
- evals 评测链路（无 evals 则跳过）
- meta.ts / SYNC.json
- 仓库目录（README.md）

### 一、引用图谱

逐技能：出边 → 目标，命中标存在；悬空单独列出。技能内 import 图用 `A → {B, C}` 这种紧凑写法。跨技能边单独汇总；零边写明「完全隔离」。

### 二、问题与观察

按严重度排。仓库级 README 未收录通常最值得处理。每条先定性（缺口 / 观察 / 杂项），再给证据。标识符分类结果放这里：运行时类型已由 SKILL.md 声明的，写明不构成本仓库悬空依赖。

### 三、可选改进建议

供决策，标明未执行。典型：补 README 目录、相邻技能 see-also、记录孤立节点是有意设计。统一 `reference/` vs `references/` 仅当维护者准备改上游或接受下次 sync 覆盖时才建议。

### 一句话总结

内部连通性是否健康、唯一（或最主要）实质问题是什么。
